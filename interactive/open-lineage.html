OpenLineage from first principles

Follow the money.

A small interactive lesson for people who already understand trades, books, and risk — and want a clean mental model for data lineage.

Core ideaOpenLineage is a common language for recording what a data job did: which inputs it read, which outputs it wrote, and which run did it.Think: a standard trade-confirmation format for data movement.

the asset

the strategy

the trade
3 · Financial analogy

One level deeper

A job is like a pricing strategy. A run is one valuation at 16:00. A dataset is like a position or market-data book.

Lineage tells you: “This risk number came from these positions, through this calculation, in this run.” That is provenance — not the calculation itself.

4 · Inspect an event

Choose the event’s point of view

OpenLineage events are small JSON messages. They record a change in a run’s lifecycle and its input/output datasets.

A run can emit multiple lifecycle events over time.


      
5 · The format, assembled
Think of an event as a signed handoff
The event has one envelope, then identifies the actor and the things it touched. Click each part to see what it means.
Envelope: what happened, when?
The top-level fields describe the lifecycle transition. A COMPLETE event says this particular execution finished successfully.
A message is not the lineage graph. It is one fact used to build the graph.

7 · The sequence
How lineage gets recorded
1. InstrumentAdd an OpenLineage integration to your orchestrator or job.
2. EmitThe job sends START, COMPLETE, or FAIL events.
3. CollectA backend stores events and builds a lineage graph.
4. AskExplore impact: “If raw_trades changes, what breaks?”
