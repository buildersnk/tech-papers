help_outline 01 — The Problem

Why global databases were impossible… until Spanner

Before Spanner, if you wanted a database that worked across multiple continents, you had two bad choices: eventual consistency (fast but you might read stale data) or strong consistency with high latency (correct but slow for users on the other side of the world).

psychology 5 Whys — Why global consistency was so hard

  1. Why? Messages take time to cross the ocean (physics of light).
  2. Why? You can’t instantly know what happened on the other side of the planet.
  3. Why? Clocks on different machines drift and disagree (clock skew).
  4. Why? Logical clocks (like Lamport’s) can’t see events outside the system.
  5. Why? No way to guarantee that transaction A really finished before transaction B started everywhere.

Spanner’s breakthrough: make the uncertainty of physical time itself part of the protocol.

schedule 02 — TrueTime

The clock that tells you how uncertain it is

Instead of asking for a single point in time, Spanner’s TrueTime returns an interval: [earliest, latest]. The difference is the uncertainty ε (~7 ms).

gps_fixed

Built from GPS + atomic clocks

Each datacenter has GPS receivers and atomic clocks that constantly cross-check.

update

TT.now() = [earliest, latest]

Spanner always works with the worst-case uncertainty.

The magic line

commit_ts = TT.now().latest

timeline 03 — External Consistency

Stronger than linearizability — across the planet

If T1 commits before T2 starts in real life, every machine sees T1’s timestamp strictly before T2’s. This is external consistency.

account_tree 05 — Architecture

How Spanner is built from the ground up

Spanner is a sharded, replicated, Paxos-based database. Data is automatically split and kept consistent using real clocks.

1

Tablets (shards)

Every table is split into contiguous ranges of rows called tablets.

2

Paxos groups

Each tablet lives on a Paxos group (3–7 replicas across datacenters) for fault tolerance.

3

Two-phase commit (2PC)

Transactions spanning multiple tablets use 2PC coordinated by Paxos leaders + TrueTime timestamps.

4

Lock-free reads

Read-only transactions pick a safe timestamp from TrueTime and read a consistent snapshot — no locks needed.

psychology 5 Whys — Why this architecture works at planetary scale

  1. Why split into tablets? One machine can’t hold the whole internet’s data.
  2. Why replicate with Paxos? Machines and datacenters fail constantly.
  3. Why use 2PC? You need atomicity across shards.
  4. Why integrate TrueTime? Because 2PC alone can’t guarantee external consistency across continents.
  5. Why does it feel fast? The tiny wait enforced by TrueTime is almost unnoticeable.
